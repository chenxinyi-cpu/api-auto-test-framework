# 登录接口手工测试用例设计

> **测试背景**：以 `postman-echo.com` 作为 Mock 接口（仅回显数据，不校验），模拟真实登录接口，验证正向、异常、边界场景的用例设计。真实校验逻辑将在后续 FastAPI 被测后端中实现。

| 用例ID | 场景分类 | 测试场景 | 输入数据 (username / password) | 预期结果 (真实登录接口应返回) | 实际结果 (Mock接口返回) |
| :--- | :--- | :--- | :--- | :--- | :--- |
| TC_001 | 正向 | 正确账号密码 | admin / 123456 | 200，返回 token | 200，回显对应参数 |
| TC_002 | 异常 | 用户名为空 | "" / 123456 | 400，用户名不能为空 | 200，回显 username="" |
| TC_003 | 异常 | 密码为空 | admin / "" | 400，密码不能为空 | 200，回显 password="" |
| TC_004 | 异常 | 缺少 password 字段 | 仅传 username | 400，参数缺失 | 200，json 中无 password 字段 |
| TC_005 | 边界 | 密码长度不足 (5位) | admin / 12345 | 400，密码长度不能少于6位 | 200，回显 12345 |
| TC_006 | 边界 | 密码最小长度 (6位) | admin / 123456 | 200，返回 token | 200，回显 123456 |
| TC_007 | 边界 | 密码最大长度 (20位) | admin / 12345678901234567890 | 200，返回 token | 200，回显 20 位密码 |
| TC_008 | 边界 | 密码超长 (21位) | admin / 123456789012345678901 | 400，密码过长 | 200，回显 21 位密码 |
| TC_009 | 异常 | 账号不存在 | not_exist / 123456 | 400，账号不存在 | 200，回显 not_exist |
| TC_010 | 异常 | SQL注入尝试 | admin'-- / 123456 | 403/400，拒绝非法字符 | 200，回显 admin'-- |

## Apifox 断言验证
在 Apifox 的“后置操作”中，我们添加了自动化断言，模拟代码的执行逻辑：
- **JSONPath**：`$.data.username` 
- **断言规则**：等于 `admin`
- **执行结果**：校验通过（✅）。这证明我们提取响应数据、对比预期结果的逻辑是通的，后续在 Pytest 中将以此基础编写 `assert` 语句。

## 测试小结与思考
1. **关于 Mock 接口的局限性**：`postman-echo` 只负责回显，无法进行真实的业务校验。因此表格中的“实际结果”全是 200。这就体现了**需要自己搭建 FastAPI 后端**的必要性，否则无法真正验证异常逻辑。
2. **关于手工测试的痛点**：在 Apifox 里修改 10 次参数、点击 10 次发送，效率极低且枯燥。这正是我们要学习**数据驱动自动化测试（YAML + Pytest）**的初衷，把用例数据抽离，让代码去跑。
